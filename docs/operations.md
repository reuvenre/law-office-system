# מדריך תפעול — גיבוי, שחזור והקמת לקוח

מבית **[win-solutions.co.il](https://win-solutions.co.il)**.

מסמך זה מיועד למפעיל המערכת (win-solutions), לא ללקוח הקצה.
למדריך המשתמש — ראו `/help` בתוך המערכת.

---

## הקמת לקוח חדש

```bash
npm run db:provision -- \
  --name "משרד כהן ושות׳" \
  --admin-name "עו״ד דנה כהן" \
  --admin-email dana@cohen-law.co.il \
  --password '<סיסמה חזקה>' \
  --plan pro
```

הסקריפט יוצר את רשומת המשרד, את שורת ההגדרות שלו, ואת המשתמש המנהל הראשון
(`role: admin`, `isAdmin`, `accessScope: all`). הרצה חוזרת בטוחה — המשרד מזוהה
לפי שם והמשתמש לפי אימייל, ולא נוצרות כפילויות.

לאחר מכן:

1. מסרו ללקוח את האימייל והסיסמה. את שאר הצוות הוא מוסיף בעצמו במסך **הגדרות**.
2. לכניסה עם Google — הוסיפו את הכתובות גם ל-`ALLOWED_EMAILS`, ורשמו את
   ה-redirect URI של הדומיין ב-Google Cloud Console.
3. שינוי תוכנית או מודולים מתבצע **רק** על ידי כתובת שמופיעה ב-`VENDOR_EMAILS`.
   הלקוח רואה את התוכנית שלו לקריאה בלבד.

### מודל הפריסה

פרטי הסולק (`GROW_*` / `CARDCOM_*`) ופרטי שליחת ההודעות הם משתני סביבה —
כלומר **ברמת הפריסה, לא ברמת המשרד**. לכן:

> **משרד אחד = פריסה אחת + בסיס נתונים אחד.**

זו גם ההמלצה העסקית: "בסיס הנתונים שלכם שלכם בלבד" נמכר למשרד עורכי דין טוב
יותר מכל הבטחת בידוד לוגי. בידוד הנתונים בקוד (`firm_id` בכל שאילתה ובכל
כתיבה) קיים בכל מקרה כהגנה בעומק, ומאפשר מעבר לפריסה משותפת בעתיד — אבל לא
לפני שפרטי הסולק וההודעות יעברו לרמת המשרד.

## גיבוי

### מה מגובה ואיפה

| רכיב | היכן | גיבוי |
|---|---|---|
| בסיס הנתונים | Neon (פרנקפורט) | Point-in-Time Restore של Neon |
| מסמכים | Vercel Blob | אין גיבוי אוטומטי — ראו למטה |
| קוד ומיגרציות | GitHub | היסטוריית git |
| משתני סביבה | Vercel | **אינם מגובים** — שמרו עותק מוצפן |

### Neon PITR

בתוכניות בתשלום של Neon יש שחזור לנקודת זמן. יש לוודא בלוח הבקרה של Neon
ש-**History retention** מוגדר לפחות ל-7 ימים (ברירת המחדל בתוכנית החינמית
נמוכה יותר). זהו קו ההגנה העיקרי מפני מחיקה בטעות.

### לפני מיגרציה מסוכנת

Drizzle אינו מייצר down-migrations, כך שלמיגרציה שנכשלה באמצע אין דרך חזרה
אוטומטית. לפני מיגרציה שמוחקת עמודה או טבלה:

```bash
# ענף Neon = עותק מלא ומיידי, ללא עלות אחסון כפולה
neonctl branches create --name pre-migration-$(date +%Y%m%d)
```

אם המיגרציה נכשלה — מפנים את `DATABASE_URL` לענף הזה, מתקנים, וממזגים חזרה.

### מסמכים

Vercel Blob אינו מגבה מעצמו. מסמכי לקוחות הם הנכס שאי אפשר לשחזר — לתיעוד
משפטי יש חובת שמירה של שנים. יש להריץ ייצוא תקופתי של ה-blobs לאחסון נפרד
(S3/Backblaze), או לפחות לוודא שהסנכרון ל-Google Drive דרך Make פעיל, שכן הוא
משמש בפועל כעותק שני.

## שחזור

1. **מחיקה בטעות של רשומה בודדת** — שחזור לנקודת זמן ב-Neon לענף חדש, שליפת
   השורה משם, והחזרתה. אין למשוך את כל בסיס הנתונים אחורה בגלל שורה אחת.
2. **מיגרציה שנכשלה** — הפריסה נכשלת לפני `next build` (זו הסיבה שהמיגרציות
   רצות ראשונות), כך שהקוד הישן ממשיך לרוץ מול הסכמה הישנה. מתקנים את
   המיגרציה ופורסים מחדש.
3. **פריסה תקולה** — Vercel → Deployments → Rollback לפריסה קודמת. שימו לב:
   **rollback אינו מחזיר מיגרציות אחורה.** אם הפריסה הכושלת שינתה את הסכמה,
   צריך גם לשחזר את בסיס הנתונים.

## ניטור

- **`/api/health`** — מחזיר 200 כשהאפליקציה חיה ובסיס הנתונים נגיש, 503 אחרת.
  יש לחבר אליו שירות uptime (UptimeRobot / Better Stack) עם התראה.
- **תזכורות שנכשלו** — מוצגות בראש הדשבורד של כל משרד. זו התקלה עם ההשלכות
  האמיתיות: לקוח שלא קיבל תזכורת לדיון.
- **Vercel Cron** אינו מתריע על תשובה שאינה 2xx. כדאי לבדוק את הלוגים אחרי
  06:00 ו-04:00 (שעון ישראל), או לחבר התראה חיצונית.
- **שגיאות ריצה** — Vercel → Observability → Runtime Errors. אין כרגע
  Sentry; אם מספר הלקוחות גדל, שווה להוסיף.

## משתני סביבה קריטיים

אלה נכשלים **בקול** בייצור (המערכת מסרבת לפעול) ולא בשקט:

| משתנה | מה קורה בלעדיו |
|---|---|
| `DATABASE_URL` | הבנייה נכשלת (המיגרציות רצות בזמן build) |
| `APP_URL` | חריגה — כדי שקישור פורטל לא יישלח ללקוח עם `localhost` |
| `GROW_API_BASE` | חריגה — כדי שחיוב אמיתי לא ייסלק מול ה-sandbox |
| `AUTH_SECRET` | Auth.js לא יעלה |

ואלה נכשלים **סגור** (התכונה פשוט כבויה): `ANTHROPIC_API_KEY`,
`BLOB_READ_WRITE_TOKEN`, `CRON_SECRET`, `PAYMENT_WEBHOOK_SECRET`,
`GREEN_API_*` / `TWILIO_*` / `RESEND_API_KEY`.

## לפני הפעלת סליקה חיה

1. הגדירו `GROW_API_BASE` לכתובת הייצור (ברירת המחדל היא sandbox, ובייצור
   המערכת מסרבת לפעול בלעדיו).
2. הגדירו אצל הספק את כתובת ה-webhook:
   `{APP_URL}/api/webhooks/payment/grow` (ב-Cardcom זה נשלח אוטומטית).
3. **בצעו עסקת בדיקה אחת מקצה לקצה ב-sandbox.** שמות השדות בתשובות ה-API
   (`statusCode`, `asmachta`, `sum`, `ResponseCode`, `TranzactionId`) נלקחו
   מהתיעוד הפומבי ולא אומתו מול חשבון אמיתי. שימו לב במיוחד ל-`sum` — אם
   הספק מחזיר אגורות ולא שקלים, המערכת תדחה את התשלום (הגנת
   `isImplausiblePayment`) ותכתוב שגיאה ללוג. זו בדיוק המטרה, אבל צריך לדעת
   ולתקן את היחידות.
